# I-038 deviations from the spec

Branch `idea/I-038` (worktree `C:\Users\pdunc\cyberpunk_world\.claude\worktrees\i038`).

1. **Measurement arms are switched at run time, in one browser, with time frozen.** The spec ran `capture.mjs --stats` once per arm with URL parameters. `tools/lightcheck.mjs --arms` instead loads the page once, places each pose, and switches the uniform with `window.__lightLimits(shade, count)` (the URL parameters `lshade` and `lcount` also work, as specified). Each arm is the mean of 100 raw per-frame `lighting` timestamps after 12 warm-up frames, not the smoothed overlay value. Reason: the arms then see exactly the same frame content (frozen time, same camera), so B - C is not mixed with animation or load differences. Arms are interleaved A B C per pose, three rounds.
2. **Block structure: bitmask fill plus a compaction step into per-block lists in ascending light index** (reviewer 2's first option), not the bit walk (reviewer 1). Both were built and measured (bit walk as a dev mode, since removed): lighting pass at A6 1.535 ms (list) vs 1.542 ms (walk), G3 1.579 vs 1.617 ms; thread slots (SIMT cost) at A6 0.42 M vs 2.06 M and G3 0.42 M vs 1.62 M. The list also keeps the full loop's order (lowest indices first), so a tile over 256 lights would keep the same kind of subset as main. The lists have room for every light (`MAX_LIGHTS` entries per block, 4.7 MB at 1440p), so there is no overflow and no fallback. The compaction dispatch (one 256-thread workgroup per block) runs inside the timed `lighting` pass.
3. **Mask clear outside the timed pass.** `enc.clearBuffer` on the 147 KB block-mask buffer sits just before the `lighting` compute pass (a clear cannot go inside a compute pass), so the bench's sum-of-passes metric does not include it (about 1 µs).
4. **Near-plane threshold lowered per axis** (reviewer 1): a light goes into every block column only when `vz < rp * AX / sqrt(1 + AX^2)` (rows: same with AY), not `vz < rp`. Padding is `rp = r * 1.001 + 0.01 + 1e-5 * length(vp)` (reviewer 1's relative term added).
5. **Width limit: 64 blocks per side (10,240 px), not 32 (5,120 px).** The row mask is 64 bits (two words); columns are tested in a loop. `resize()` throws above 64 blocks. This is above WebGPU's default 8,192 px texture limit, so it never triggers.
6. **Verify variant also reports SIMT cost.** Besides disagreeing tiles, tiles over 256, the longest walk and total tests, the `lverify` variant reports "thread slots" (per 32-thread warp, the busiest thread's tests x 32). Identity is checked on the full passing set before the 256 cut (count, XOR and sum of `pcg(i)`), as both reviewers asked.
7. **Fuzz lights are generated on the CPU** (`window.__lightFuzz(n, seed)` in `dev.js`): black lights in the unused slots, placed behind the camera, across its plane, beside it and on block edges (radii 1-300 m). The comparison itself runs in the same GPU shader as the real path, so rounding is real.
8. **Files touched:** `renderer.js` (lighting pass), `dev.js` (dev hooks: arms, stats read-back, fuzz, raw pass timings) and the new `tools/lightcheck.mjs`. The production lighting shader keeps the `LU` uniform (binding 7) with defaults 256 / 8,192; `LU.y` limits the block-list length, as in spec section C. A dev URL parameter `lcull=full` compiles main's full loop in the same build, for A/B checks.
9. **Overflow rule did not apply:** no tile passes more than 256 lights on main at the 14 eval poses or the 120 bench-path points (most: 65 at 2560x1440). The consecutive-frame stability check of the motion bursts was still run against main (results.md).
